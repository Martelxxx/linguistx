Linguist-X Passenger

This page documents the complete passenger/mobile application as it exists in this release: visual invariants, state model, backend boundaries, APIs, guest authorization, local fixture, provider adapters, caching, tests, checklist governance, and the rules a developer must follow to continue the work without accidentally undoing the product experience built across more than 75 iterations.

Scope boundary: this documentation covers only the passenger application in this package. Fleet management, remote support, commissioning, management center, and evidence systems are separate Linguist-X workstreams.

1. Product invariants

These are deliberate product decisions, not incidental implementation details. A maintainer should preserve them unless the product owner explicitly authorizes a UX change.

Passenger journey

Welcome/language → flight discovery or scan → explicit flight confirmation → Live translation experience. The application is account-free.

Visual language

Centered identity, quiet information hierarchy, soft neumorphic/glass surfaces, living orb / bridge-X transition, restrained color, responsive phone frame, and reduced-motion support.

Translation truthfulness

Integration mode never substitutes demo announcements for unavailable live media. Fixture captions are visibly prefixed [TEST DATA].

Authorization boundary

Public passenger navigation may continue when translation access is denied. Protected guest translation events must not.

Privacy posture

No passenger account. Provider credentials and upstream guest bearer tokens stay server-side. Camera/barcode content and translated content must not enter logs.

Internal controls

The checklist, fixture scenario selector, and Demo/Integration controls are desktop development chrome outside the phone. They are not passenger UI.

2. Quick start

Recommended local development

python3 start.py
# open http://127.0.0.1:8765/

start.py sets LX_NO_SETUP=1 and LX_ENABLE_FIXTURE=1, then replaces itself with run.py. The local loopback fixture becomes available to the desktop Integration toggle. It is simulated contract data, not Wordly.

Passenger-only surface

http://127.0.0.1:8765/passenger-only.html

This removes the internal checklist and fixture controls. It is the closest browser representation of the passenger-facing surface in this package.

Production-style ASGI transport

python3 -m pip install -r requirements-production.txt
python3 start_asgi.py
Do not confuse “production-style transport” with production certification. Live provider integration, actual infrastructure, capacity testing, deployment controls, and native/mobile acceptance remain separate gates.

3. Architecture at a glance

Passenger HTML/CSS/JS→/api/* application boundary→run.py / passenger_asgi.py→Gateway + provider adapters→Approved external services

The browser intentionally speaks only to same-origin application APIs. It does not call the guest gateway with a service credential. integration_bridge.py translates the application’s guest-session operations into a small reviewed upstream contract. The browser receives an opaque lx_guest cookie handle; the corresponding upstream guest token remains server-side.

5. Frontend model

v78 Wordly launch transition. The passenger document now opens with a two-second centered Powered By + Wordly wordmark. The transition is implemented as a runtime-measured shared-element flight: temporary fixed-position visual copies animate to the actual #welcome .home-powered text/logo rectangles, then are destroyed and the untouched Home footer is revealed. This avoids hard-coded device coordinates and keeps the Home screen authoritative. The feature is isolated from navigation/session state and falls back to a simple fade for prefers-reduced-motion.

The frontend remains deliberately framework-free in this release. The two HTML files contain the visual system, screen markup, application state, localization map, animation logic, scanning workflow, Demo behavior, and Integration client. This avoids a framework rewrite that could alter the established experience.

6. Backend model

Local core

run.py owns reusable provider functions and the local BaseHTTPRequestHandler. It loads optional local credentials, normalizes provider responses, bounds downloads/bodies, maintains small caches, serves static assets, and forwards guest-session work through integration_bridge.GATEWAY.

ASGI adapter

passenger_asgi.py deliberately reuses the same core provider functions to minimize behavior drift. Blocking network functions are executed in Starlette’s thread pool. Security middleware attaches request IDs and baseline headers without logging sensitive request content.

Configuration policy

runtime_security.read_settings() validates LX_ENV, port, fixture/LAN constraints, and the production public origin. Production forbids the fixture and requires a noninteractive start. The guest gateway itself separately requires shared Redis state when configured in production.

7. Translation integration boundary

The code does not assume an undocumented Wordly REST API. It defines an AV-ation-controlled gateway contract that can later be backed by the approved provider integration.

9. Security and privacy invariants

  • Credential isolation: service keys remain server-side. Browser integration uses only same-origin APIs.
  • Gateway transport: non-loopback gateway URLs must be HTTPS. Credential-bearing redirects are rejected.
  • Guest cookie: HttpOnly, SameSite=Strict, scoped to /api/integration; Secure in production.
  • Guest state: browser receives an opaque random handle, not the upstream guest token.
  • Invite binding: when supplied, an invitation must resolve to the discovered flight and exact session before join.
  • Revocation: upstream 401/403 state/event failures evict the local grant. Negative fixture scenarios clear/reject grants.
  • Request bounds: JSON bodies and upstream downloads have explicit maximum sizes.
  • Origin policy: production POSTs require the exact configured HTTPS public origin.
  • Host policy: ASGI production rejects unexpected Host values.
  • Headers: nosniff, no-referrer, frame denial, restricted permissions, and HSTS in production.
  • Audit logging: fixed metadata schema only: event, status, latency, request ID, timestamp.
  • Fixture isolation: fixture cannot run in production or LAN mode; developer controls require loopback ownership.
Future security work: deployment-level rate limiting, edge/WAF policy, secret-manager integration, provider-specific authorization review, formal threat modeling, and independent penetration testing cannot be proven by this local package alone.

10. Guest and translation lifecycle

Browser-visible lifecycle

Demo↔Integration selected→Session discovered→Guest joined→Connected / reconnecting / unavailable→Leave / expire / ended

Server guest record

A server-side mapping contains the upstream token, expiry, session ID, selected language, and event sequence. In local development it is in memory. In configured production mode, the gateway requires the Redis-backed stores from shared_guest_store.py so workers do not hold contradictory authorization state.

Stale-content rule

Language, flight, session, mode, expiry, or denied access clears transient caption state. The client must not leave an old caption on screen while representing a different translation context.

12. PWA and caching rules

sw.js caches a small static shell and local visual assets. Navigation to the app shell is network-first with offline fallback. Same-origin GET assets on the explicit shell list are cache-first.

Never cache /api/. Guest state, translated captions, authorization responses, and service status must not be persisted by the service worker.

Changing shell assets requires a cache-name bump so older installed previews do not retain stale CSS/JavaScript.

13. Accessibility behavior to preserve

  • Keyboard focus indication for interactive controls.
  • Semantic roles and labels on dialogs, live status regions, scan areas, and controls.
  • Text-only translation mode and adjustable caption scale.
  • Reduced-motion support through OS preference and app behavior.
  • Readable failure states that do not depend on color alone.
  • Explicit control labels for language, recent announcements, flight change, and settings.

A formal WCAG audit remains separate from these implementation affordances.

16. Deployment path

Local development

start.py → run.py + loopback fixture. This is optimized for repeatable product testing, not internet exposure.

Production-style application server

passenger_asgi:app is the supported web transport. Production mode requires an HTTPS public origin and, when a gateway is configured, shared Redis guest state. Dockerfile.candidate documents a conservative one-worker container entry point but is explicitly not a scale certification.

Before a real external deployment

  • Use reviewed infrastructure, TLS termination, secret manager, observability, rate limiting, and deployment rollback.
  • Verify the real translation gateway/provider contract and media delivery.
  • Load-test the actual architecture at a defined concurrency/event rate.
  • Run security, accessibility, browser/device and failure-mode acceptance tests.
  • Bundle/review browser dependencies and establish CSP compatible with the final asset architecture.

17. Safe change protocol

  1. State the intended behavior change before editing.
  2. Identify whether the change touches passenger UX, application API, guest authorization, provider adapter, cache, or internal tooling.
  3. For non-UX work, do not opportunistically “clean up” HTML/CSS/animation.
  4. Add or update automated tests first for security-sensitive regressions.
  5. Keep run.py and passenger_asgi.py semantically aligned for shared routes.
  6. If guest/session semantics change, update INTEGRATION_CONTRACT.md.
  7. If architecture/config/routes/state change, update this page and DEVELOPER_HANDOFF.md.
  8. Run the full test suite and no-network verification.
  9. Manually compare the affected screens and interaction path against the previous approved release.
  10. Update release/QA documentation; never infer contractual completion from implementation alone.

18. Troubleshooting

Integration says gateway URL/token missing

For local fixture testing, start with python3 start.py. Confirm /api/dev/fixture reports enabled: true. If an older process owns port 8765, stop it before relaunching.

Fixture is disabled

start.py explicitly enables it. Direct python3 run.py does not unless LX_ENABLE_FIXTURE=1 is present. Fixture use is intentionally rejected in production and LAN mode.

Flight / voice / weather unavailable

These optional services use server-local environment values or the current package’s .env. v76+ does not harvest credentials from historical folders.

Guest access remains blocked after a negative fixture scenario

Return the fixture scenario to Healthy. Revocation/invalid-invite scenarios intentionally clear existing grants; a new guest join is required.

Checklist edits do not appear

Edit requirements-progress.json, then run python3 sync_progress.py. The browser does not write checklist acceptance back to disk.
